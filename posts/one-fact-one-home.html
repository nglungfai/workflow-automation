One Fact, One Home: How an Agent System Remembers

Case Study · 4 min read

Every AI conversation ends with total amnesia. The agent that shipped a release yesterday wakes up today knowing nothing about the deploy trap it discovered, the style correction you made, or the decision you reached together. The naive fix is to write everything down everywhere — and that fails in a worse way, because now there are five copies of every fact, they disagree within a month, and the agent confidently acts on the stale one. The publishing pipeline behind this site claims that "every failure becomes a lesson the agent keeps." This post is about the architecture that makes that true — where lessons actually live, and what stops them from rotting.

Three stores, one rule

Everything this system was designed to know lives in exactly one of three places, split by what kind of fact it is — because different kinds of facts change at different speeds and rot in different ways.

The skill is the agent's standing instructions: the post template, the browser-publishing procedure, the deploy-failure recovery playbook, the content rules. It loads automatically whenever relevant work starts. The project doc was a living PRD on Confluence: what was decided, what shipped when, what's still open, and why — the file a new collaborator (human or agent) would read first. It has since been retired; see the update below. Agent memory is deliberately the smallest: pointers to the other two, plus the handful of facts that belong nowhere else. The rule that holds it together: a fact lives in exactly one store, and the others link to it. Copies are how documentation lies to you — two versions of a fact means one of them is wrong and you don't know which.

Update, Nov 2026: the project doc is gone. It was the store that cost the most to maintain and the one the monthly audit kept finding stale, so we stopped updating it on 2026-10-31 rather than keep paying for a home that wasn't earning its keep. The system now runs on two stores, the skill and agent memory, plus one more rule: the shared working folder is the source of truth for the site's content, and the repository and live site are a mirror of it. A drift check compares the two at the start and end of every session, and the monthly audit reports any difference. Deleting a home is the same rule applied honestly: if a fact has no store worth keeping it in, it doesn't get a copy.

How lessons get in

Any work session that changes the system's shape ends with a sync sweep — three questions, answered while the context is still hot: Did this make a procedure stale? Update the skill. Did it change a decision or status? That used to mean updating the project doc; now it means recording it in the skill, or in memory when no procedure is affected. Did it break a pointer, or create a fact with no home? Update memory. The sweep is why the skill's version history reads like an engineering log: v1 gave the human exact steps to execute; v2 let the agent push directly; v5 encoded a deploy-recovery playbook learned from four production failures; v6 encoded the white-label rules and a commit-verification discipline learned from a silently dropped commit. Each version is a scar with documentation.

How rot gets caught

Sweeps get missed — that's a when, not an if. So the backstop is an anti-entropy audit: a scheduled agent reads the live site once a month and checks every claim the stores make against what's actually deployed, and reports any drift between the working folder and the published copy. Stale procedure in the skill, status row that no longer matches reality, dead pointer in memory — each becomes a line in a report for human review. The audit proposes; it never decides. The design assumption is worth stating plainly: documentation is presumed to drift, so the system doesn't rely on discipline to prevent drift — it schedules the job of finding it.

The questions worth asking

"Why not one big document?" Because procedures, decisions, and pointers have different lifecycles. A procedure changes when a lesson is learned; a decision changes rarely and its history matters; pointers change constantly and are worthless when stale. In one document, the fast-changing parts bury the stable parts, every edit risks the whole file, and nobody can tell which sections still hold. Splitting by rot-rate is the same reason databases separate hot and cold data.

"The agent edits its own instructions — what stops that from going wrong?" The same gate that governs everything else: the agent drafts skill updates, but a human reviews and installs them. Instructions are versioned artifacts, not a scratchpad — the agent can propose that its own procedure was wrong, and it regularly does, but it can't quietly rewrite the rules it operates under.

"What happens when the stores disagree anyway?" For what the public sees, the live site wins — it's the one artifact that can't drift from itself. For what is intended, the working folder wins. A disagreement isn't silently patched; it's filed as a finding, a human rules on which store lied, and the fix includes asking why the sweep missed it. Disagreement is treated as a bug in the process, not just an error in a file.

So what?

Most agent demos are impressive for one session and amnesiac by the next. The unglamorous half of agent engineering — the half that makes the publishing pipeline compound instead of reset — is exactly this: deciding where facts live, how lessons get written in, and who catches the rot. Context windows end. Systems shouldn't. The same architecture runs the private production workflows this site describes; the version you're reading about is the one whose paper trail is public.
