One Fact, One Home: How an Agent System Remembers

Case Study · 4 min read

Every AI conversation ends with total amnesia. The agent that shipped a release yesterday wakes up knowing nothing about the deploy trap it found, the style correction you made, or the decision you reached together.

The naive fix is to write everything down everywhere. That fails worse. Now there are five copies of every fact, they disagree within a month, and the agent acts on the stale one with full confidence.

The publishing pipeline behind this site claims that "every failure becomes a lesson the agent keeps." This post shows where those lessons live, what it cost to keep them there, and where the design still leaks.

Three stores, one rule

Every fact lives in exactly one store, split by how fast that kind of fact rots.

The skill holds the agent's standing instructions: the post template, the browser-publishing procedure, the deploy-recovery playbook, the content rules. It loads automatically when relevant work starts.

The project doc was a living PRD on Confluence: what was decided, what shipped, what's still open, and why. It has since been retired (see the update below).

Agent memory is deliberately the smallest: pointers to the other two, plus the few facts that belong nowhere else.

The rule that holds it together: a fact lives in exactly one store, and the others link to it. Two versions of a fact means one is wrong and you can't tell which.

Update, Nov 2026: the project doc is gone. It cost the most to maintain and was the store the monthly audit kept finding stale, so we stopped updating it on 2026-10-31. The system now runs on two stores, plus one more rule: the shared working folder is the source of truth for site content, and the repository and live site are a mirror. A drift check compares the two at the start and end of every session. Deleting a home is the same rule applied honestly: if a fact has no store worth keeping it in, it gets no copy.

How lessons get in

Any session that changes the system's shape ends with a sync sweep: three questions, answered while the context is still hot.

Did this make a procedure stale? Update the skill. Did it change a decision or status? Record it in the skill, or in memory when no procedure is affected. Did it break a pointer or create a fact with no home? Update memory.

The sweep is why the skill's version history reads like an engineering log. v1 gave the human exact steps. v2 let the agent push directly. v5 encoded a recovery playbook learned from four production failures. v6 added the white-label rules and a commit-verification step after one commit was silently dropped.

Each version is a scar with documentation.

How rot gets caught

Sweeps get missed. That's a when, not an if, so the backstop is a scheduled anti-entropy audit.

Once a month an agent reads the live site and checks every claim the stores make against what's deployed. It also compares the working folder with the published copy. Each stale procedure, mismatched status row, or dead pointer becomes a line in a report for human review. The audit proposes; it never decides.

The design assumption: documentation drifts, so the system schedules the job of finding the drift instead of relying on discipline to prevent it.

What still leaks

A fact that is wrong in two places passes the audit. The audit compares stores against the live site and each other. If the skill and the site agree on something false, nothing flags it.

The human gate is a queue. The agent drafts skill updates, but a person reviews and installs them. That keeps the agent from quietly rewriting its own rules, and it also means a lesson can sit unlearned until someone reads the report. A report nobody reads is drift with paperwork.

The sweep is still a habit. It's a three-question checklist, not an enforced step. The audit exists because the sweep gets skipped.

The project doc earned its retirement late. It duplicated what the commit history and the skill already said, and I kept paying for it until the monthly audit made the cost undeniable. The "one home" rule should have flagged it on day one.

What I'd do differently

Start counting audit findings by cause from the first month: missed sweep, bad pointer, or genuinely new drift. That one metric would show whether the sweep is working or whether the audit is quietly doing its job.

I'd also ask, before adding any store, which existing store its facts would otherwise live in. If the answer is "one we already have," skip the new home.

The bottom line

Most agent demos are impressive for one session and amnesiac by the next. What makes the publishing pipeline compound instead of reset is deciding where facts live, how lessons get written in, and who catches the rot.

Context windows end. Systems shouldn't.
