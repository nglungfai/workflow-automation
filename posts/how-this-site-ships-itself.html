How This Site Ships Itself: Inside an Agent-Run Publishing Pipeline

Case Study · 5 min read

The homepage makes a claim you should doubt: every page here was drafted, committed, and deployed by the same kind of workflow it documents.

This post backs it up with one real release: what the AI did, what a person did, what broke, and how it was caught. The paper trail is public: the commit history (the site's save-and-publish log) and the deploy log.

A person describes what should exist. An agent writes it. The person approves. The agent publishes by operating the same website a human contributor would use, clicking the same buttons. A human touches exactly two steps.

One release, 17 published changes

The example is this site's biggest release: the overhaul that turned an internal knowledge base into this public portfolio.

Every page was rewritten. Two articles were renamed, with every link to them updated. Four files were deleted. Three animated illustrations had a label baked into the pixels, so they were edited frame by frame and re-uploaded.

Sequencing mattered. New pages went up before anything linked to them, and old pages came down last, so no visitor hit a broken site.

The hard part: publishing like a person

The agent has no publishing keys and no direct line to the server. By design, it can only do what a person with a browser could.

GitHub's editor won't accept text from a program, so the agent does what hands do, synthetically: a "select all" keystroke and a "paste" event, the same signals a keyboard and clipboard produce. For the technically curious:

cm.dispatchEvent(new KeyboardEvent('keydown',
  {key:'a', code:'KeyA', metaKey:true, bubbles:true, cancelable:true}));
const dt = new DataTransfer();
dt.setData('text/plain', newContent);
cm.dispatchEvent(new ClipboardEvent('paste',
  {clipboardData: dt, bubbles: true, cancelable: true}));

The failures here are silent. Select the wrong way and the editor quietly pastes a second copy of the page below the first. Sometimes the automation reports "failed" when the paste actually worked, so a retry would double the content.

The working rule: never trust the report, check the result. After every paste, the agent screenshots the end of the file: right line count, page ends exactly once.

Trust nothing, fingerprint everything

Before saving, the agent computes a fingerprint of what the page should say: a short code where a one-character difference changes everything. It refuses to save unless the rebuilt page matches. It also sweeps for terms not allowed on the public site.

That paranoia paid off mid-release. One page came out 216 characters short. The cause was invisible spacing differences left by an old hand edit. The fingerprint, built to ignore spacing, proved the content matched, so the release went on with the discrepancy understood rather than ignored.

After the final change, the same audit ran against the live site: banned terms zero, renamed pages resolving, retired addresses correctly dead.

The publishing infrastructure also failed twice mid-release. Neither needed a fix, because each publish pushes the entire site and the last successful one carried everything. The recovery playbook for failures that do need action was learned once, the hard way, then written into the agent's instructions.

The system caught its own mistake

While drafting this very post, an audit of the release's logs found that one of the 17 changes had never landed. A button click missed and the edit was silently discarded.

It went unflagged for a day because the routine check looked at public pages, and this file wasn't one. A verification gap, found by the verification habit, fixed in the release that shipped this post.

The checklist now reconciles intended changes against the actual log, every release. The pitch isn't that agents don't make mistakes. It's that every mistake gets caught by a check, and every check becomes standing procedure.

The same error doesn't ship twice.

Why a browser, and why trust it

Why click through a website? The agent's blast radius is a person's blast radius. Most tools worth automating (dashboards, admin consoles, vendor portals) have no programmer's entrance at all. The browser is the universal one.

Why not make 17 changes by hand? A person could, in an afternoon. But the afternoon repeats every release, and human effort doesn't compound. Every lesson goes into the agent's standing instructions, so the next release starts smarter, and the checks run identically on the first edit and the seventeenth.

Why trust it at all? You don't. Nothing publishes without human approval, and nothing is assumed to have worked without a check. The trust sits in the verification, not in the AI.

What still leaks

Prompt injection is not solved. The agent reads web pages in a real session, so a page can carry text crafted to look like instructions.

The defense is architectural: page content is data, destinations are fixed, and nothing publishes unsigned. The worst case here is a bad commit to a public repo, which is visible and revertible. Injection remains an open problem industry-wide.

The checks verify mechanics, not writing. A fingerprint can't prove a paragraph is good, so a human checks the writing and each correction becomes a standing rule. What's missing is a formal evaluation harness: scored test cases per skill, re-run when models change.

A routine check only sees what it looks at. The dropped commit survived a day because the check covered public pages and not that file. The log reconciliation closes that gap.

What I'd do differently

Reconcile intended changes against the actual log from the first release, not after a commit went missing.

I'd also build the evaluation harness earlier. Mechanical checks say the page landed, not that the writing holds up.

The bottom line

A website that publishes itself is a parlor trick. The operating model is not. Swap "publish a page" for bulk-creating audience segments in a live production tool, turning meeting notes into partner-ready documents, or auditing content monthly for drift. The same loop runs them all: describe, draft, gate, execute, verify, keep the lessons.

Those systems are private. This one you can audit.
