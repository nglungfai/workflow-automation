Prompt Engineering vs. Context Engineering vs. Harness Engineering vs. Loop Engineering

Concepts · 6 min read

These four terms get used interchangeably in agent discourse. They describe four layers of the same system, and each fails for a different reason.

If your Cowork workflow is underperforming, the fix depends on the broken layer. Rewording instructions when the real issue is missing tool access or no verification step burns turns for nothing.

The vocabulary arrived in layers. Prompt engineering came with the ChatGPT era, in 2022. Context engineering followed in 2025, as agents started juggling multi-turn state and long context windows. Harness engineering came in 2026, as the scaffolding around the model became the bottleneck.

Loop engineering arrived in mid-2026, for systems that decide on their own when to invoke the agent at all. Addy Osmani popularized the term, building on work from Peter Steinberger and Anthropic's Boris Cherny.

Prompt engineering: what to ask

Single turn · everything already provided

This is the layer everyone starts with, and the one this site already covers in depth. It covers a single turn: the wording, structure, and constraints of one request.

It's necessary, and the smallest lever in the stack. A perfect prompt still fails if the model lacks the right information or tools.

Context engineering: what the model needs to know

What information the model can see

Context engineering curates what gets loaded into the model's working memory: which files, prior turns, retrieved documents, and schema definitions. The goal is a model that answers without guessing.

Past toy tasks, this matters more than wording. Cramming in everything "just in case" hurts as much as omitting the one fact that mattered.

In our world, that's the difference between asking Cowork to "summarize the [client] audience" cold and pointing it at our platform's MCP tools, so it pulls live composition data instead of working from stale training knowledge or a half-remembered Slack thread. The prompt barely changed. What the model had in front of it did.

Harness engineering: how the whole thing operates reliably

Multi-step · tools · safety gates

Harness engineering is the operational layer around the model: the toolchain it can call, the limits on what it may touch, the feedback that says whether an action succeeded, and the lifecycle that carries state across context windows.

Context engineering optimizes what's inside one window. Harness engineering handles a task too big for one: context resets, structured handoffs between phases, and phase gates that keep the task coherent while working memory is wiped and rebuilt.

A scoped tool list, a checklist to satisfy before the next phase, and a verification step before anything ships: that's harness, not prompt.

The agent-pm skill's rule that Slack drafts always route to a review channel before reaching a real recipient is a harness constraint. It doesn't ask the model nicely to be careful. It removes the ability to skip the check.

Loop engineering: the system that decides when to prompt at all

Runs unattended · self-evaluates

Loop engineering is the newest and most autonomous layer. Instead of a human typing each prompt, you build the system that decides what work exists, acts on it, verifies the result, remembers what's done, and decides what comes next, with no human in each cycle.

A scheduled Cowork task that checks a data pipeline every morning and pings you only when something is wrong is a small version of this.

The failure mode here isn't a bad response. It's a system that keeps confidently doing the wrong thing on a loop, because nothing verifies its output before it acts on step two.

Which layer is actually broken?

SymptomLikely layer
Response is vague, wrong format, or misses the deliverablePrompt
Response is confidently wrong or stale despite a clear promptContext
Agent can't complete a multi-step task, loses state, or skips a required checkHarness
A recurring/scheduled agent keeps taking the wrong action unattendedLoop

For a Product org, this decides where engineering time goes. Prompt quality is a training problem: coach the team, and see Prompting Tips That Actually Move the Needle in Cowork. Context and harness quality are skill-design problems: scoping a tool list, adding a phase gate, requiring review before something goes external.

Loop engineering is where scheduled tasks and always-on monitoring live, and where a verification step matters most.

Which layer does this task need?

The table above diagnoses a task that's already misbehaving. Before building anything, ask forward: escalate one layer at a time, and only once the current layer has a demonstrated, specific gap. Never start from loop engineering because it feels more automated.

LayerExample tasks
PromptSlack drafts, paragraph rewrites, inline SQL against a pasted schema, summarizing an attached doc
ContextLive platform MCP lookups, pulling the right Confluence page before a spec, real contract terms before a renewal email
HarnessMulti-system partner POCs, bulk audience creation with per-row validation, onboarding flows gated on confirmation
LoopNightly audience re-scoring, partner SLA monitoring, recurring competitive-intel sweeps

When each layer is over-engineering

Every layer above the one a task needs is overhead: added latency, failure surface, and maintenance, for a benefit nobody collects. It's the impact-vs-effort lens you'd apply to a roadmap decision.

LayerOver-engineering signalCost when misapplied
ContextFull context already fits in the prompt itselfA retrieval step adds a moving part — stale index, wrong doc, silent miss — to save one copy-paste
HarnessTask is genuinely one or two stepsTool scoping and checklists add review overhead and rigidity to something that was never going to drift
LoopNobody actually needs it to act without a human deciding each timeBecomes ignored alert noise, an unowned maintenance liability, or a source of compounding errors from unverified output

A tell across all three: if you can't name the failure the extra structure prevents, you're adding ceremony, not reliability.

Before automating anything into a loop, don't ask whether it could run on a schedule. Almost anything could. Ask whether it must act without a human deciding each time, and whether you can catch it doing the wrong thing.

If the honest answer is "we just wanted it off our plate," that's a one-off task wearing a loop's clothing.

That's vocabulary history, not a benchmark. This post doesn't measure how often each layer causes a failure.

Where this breaks

The vocabulary is young. Loop engineering dates from mid-2026, so treat the nesting as a working model, not a standard.

Symptoms overlap. A confidently wrong answer can be stale context, a harness with no verification step, or a loop acting on unchecked output. The symptom table says where to look first, not what is wrong.

The top layer is the least supervised. Nothing watches a loop turn by turn, so a missing verification step costs the most there.

What I'd do differently

Start every task at the prompt, and add a layer only when a specific failure shows up. Before building it, write down the failure it prevents.

The bottom line

Four layers, four failure modes. A prompt fix can't repair a broken harness, and a better harness can't fix a loop with no verification step.

Each layer is additive, so escalate only on a demonstrated failure.

Name the failure the extra structure prevents, or don't add it.
